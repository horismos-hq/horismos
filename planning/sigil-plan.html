From Language to Framework: an Ontology-First Agent Runtime

The pivot in one line: keep sigil-lang as reference, start fresh in ../sigil — a neuro-symbolic framework whose center of gravity is an ontology the agent lives inside, not a language humans write. Rust core, Python bindings. This file lives at sigil/planning/sigil-plan.html and is republished on demand.

Symbolic — deterministic, traceable, decides Neural — perceives and proposes, never decides

01 · Why pivotThe thesis

sigil-lang proved the machinery works: a full Rust implementation (lexer → parser → bytecode VM), Rete-lite forward chaining, backward chaining with proof trees, a constraint solver, BDD-based formal verification with counterexamples, auditable traces, and a neural bridge with six pluggable model backends — 1,200+ tests passing. What it didn't prove is that anyone wants to learn a new language to get those guarantees.

The market signal points the other way. Apollo-1 raised $60M on what is architecturally a typed-state machine plus rules engine wrapped around an LLM — no user-facing language at all. Scallop, the strongest academic neuro-symbolic system, ships as a Rust library with Python bindings. The value is the runtime with guarantees, not the surface syntax.

So the pivot: the product is a framework where an LLM agent's world-state is typed instances of an ontology, and everything the agent "knows" or concludes flows through a deterministic reasoning substrate. The LLM perceives and proposes; the ontology and its reasoner hold the truth.

02 · What it isOntology-first agent framework

The sharpest way to see it: Claude Code is "just" a loop with tool uses — the loop is trivial; what makes it work is everything grounding it. We are not building another agent framework that lets you talk to an LLM and reason about tool calls. We're building the thing that grounds the loop: the ontology is the world-state, the reasoning, and the agent loop itself — one artifact, expressed in RDFS-plus (RDFS with the constraint and rule extensions we need), authored by subject-matter experts per domain. LLMs and tools already exist for every domain; the missing, novel piece is the executable ontology and the runtime that runs it.

The ontology plays three runtime roles:

  • Typed world-state the agent lives in. Every entity, relation, and state change is an instance of ontology classes. The LLM never holds raw state — it reads and writes a validated, typed world model. Invalid states are unrepresentable, not merely flagged.
  • Reasoning substrate. The ontology carries inference: class hierarchy and subsumption, rules, forward and backward chaining over instances. The agent asks "what follows from what I know" and gets a deterministic, fully traced answer with a proof tree.
  • The loop and workflows themselves. Agent loop and workflow are not different things — they are one. Steps, transitions, tool invocations, and completion conditions are ontology terms the runtime executes, not host-language orchestration code. Changing the workflow means editing the ontology, not the framework.
Agent loop (ontology-declared, runtime-executed) — perceive NL → extraction into ontology terms → reason → act. The loop's steps and workflows are ontology data, not framework code. Neural proposes.
Ontology schema (Rust) — classes, properties, relations, constraints, cardinalities. The contract everything else type-checks against.
World-state store (Rust) — typed instances, validated mutations, versioned snapshots. The agent's memory of record.
Reasoning engine (Rust) — forward/backward chaining, subsumption, constraint checking — every conclusion carries a trace.
Guarantees (Rust) — BDD verification of rule sets: completeness, conflicts, dead rules, termination — with witnesses.
Neural bridge — pluggable model backends, confidence thresholds, mandatory fallbacks — the only door for non-determinism.

The core philosophy survives the pivot intact: neural for perception, symbolic for reasoning; deterministic by default; traces as fundamental output. What changes is the interface — a Python/Rust API instead of a surface language. A DSL can return later as an optional authoring format; it is no longer the front door.

Candidate domainsWhere SME-built ontologies win

The framework's bet: LLMs and tools already exist for every domain — the missing piece is the executable ontology, and the people who can author it are subject-matter experts, not ML engineers. So the right first use case is a domain where (a) the knowledge genuinely lives in experts' heads or policy documents, (b) decisions must be explainable, and (c) a vanilla LLM agent demonstrably fails. Six candidates, then a recommendation.

UC-1
Airline & travel customer service (the τ-Bench arena)

SME: operations & fare-policy teams. Ontology: tickets, fare classes, change/cancel/refund policies, loyalty tiers; workflows: rebooking, refunds, disruption handling. Tools: booking APIs (τ-Bench mocks them). Why ontology-first wins: policy compliance is exactly what unscaffolded LLMs fail — Claude 4 Sonnet scores ~60% on τ-Bench-Airline; Apollo-1 self-reports 90.8–92.5% with a typed-state architecture. The kicker: a public benchmark with published baselines means the thesis is provable with a number, in the same arena our closest competitor chose.

UC-2
Insurance claims processing

SME: claims adjusters, underwriters. Ontology: policies, coverage, exclusions, claim lifecycle states; workflows: FNOL → triage → adjudication → payout. Tools: policy systems, document extraction (LLM), payment rails. Why ontology-first wins: every denial needs a defensible explanation — proof trees are the product, not a feature. Strong commercial pull; no public benchmark, so proof comes from a design partner.

UC-3
Regulatory compliance (KYC/AML onboarding & monitoring)

SME: compliance officers. Ontology: entity types, jurisdictions, thresholds, obligations, escalation paths; workflows: onboarding checks, transaction monitoring, SAR filing. Why ontology-first wins: regulators require deterministic, auditable decisions — "the model felt suspicious" is not a filing. Traces map directly to audit evidence. Rules change constantly; SMEs editing the ontology beats redeploying prompt chains.

UC-4
Clinical triage & care pathways

SME: clinicians. Ontology: symptoms, vitals, contraindications, protocol steps — and here RDFS-plus pays off immediately: SNOMED CT and FHIR already exist as importable vocabularies. Why ontology-first wins: safety-critical, trace-mandatory. Caveat: heaviest regulatory lift; best as a flagship later, not the proving ground.

UC-5
SRE & incident response runbooks

SME: senior SREs. Ontology: services, dependencies, alert semantics, runbook procedures with preconditions/effects; workflows: diagnose → mitigate → verify → postmortem. Tools: kubectl, dashboards, pagers — all reachable via MCP today. Why ontology-first wins: the sharpest contrast with "Claude Code for infra": same loop, but a 3 a.m. remediation only executes if its ontology preconditions hold. Great dogfooding domain; developer-audience demo, weaker enterprise pull than UC-2/3.

UC-6
Contract obligations management

SME: legal ops. Ontology: parties, clauses, obligations, deadlines, renewal/termination conditions; workflow: LLM extracts clauses → deterministic obligation tracking, deadline inference, conflict detection. Why ontology-first wins: clean neural/symbolic split — extraction is perception (neural), obligation logic is reasoning (symbolic). Narrow enough for a small ontology; less "agentic" than the others.

1 · The artifact the SME authors

There is no "app code" in a Sigil deployment. A clinician (with an ontology editor or plain text) authors one artifact — an RDFS-plus ontology that declares the domain and the workflow. This file is the application; the runtime executes it.

triage.ttl — authored by the SME, versioned like code 
# -- Domain: classes, properties, constraints ----------------------
:Patient a rdfs:Class .
:heartRate a rdf:Property ;
    rdfs:domain :Patient ; rdfs:range xsd:decimal ;
    sigil:unit "bpm" ; sigil:min 0 ; sigil:max 300 .   # invalid vitals are unrepresentable

:ChestPain rdfs:subClassOf :Symptom ;
    owl:sameAs sct:29857009 .                    # anchored to SNOMED CT — imported, not reinvented

# -- Reasoning: rules live in the ontology --------------------------
:r1 a sigil:Rule ;
    sigil:when  [ :heartRate sigil:exceeds 120 ; :hasSymptom :ChestPain ] ;
    sigil:then  [ :acuity :Immediate ] ;
    sigil:explain "Tachycardia with chest pain — immediate track" .

# -- Workflow: the agent loop is ontology data, not framework code --
:Triage a sigil:Workflow ; sigil:startsAt :Intake .

:Intake a sigil:PerceptionStep ;                # the ONLY place neural exists
    sigil:extracts :Patient, :Symptom ;
    sigil:model "claude-fable-5" ;
    sigil:confidence 0.85 ;
    sigil:fallback :EscalateToNurse ;           # mandatory — low confidence never guesses
    sigil:next :Assess .

:Assess a sigil:ReasoningStep ;
    sigil:goal [ :acuity sigil:isAssigned true ] ;
    sigil:next :Route .

:Route a sigil:ActionStep ;
    sigil:tool :ehr.assign_queue ;
    sigil:requires [ :acuity sigil:isAssigned true ] .  # unmet precondition = step cannot fire

Python is the front door for builders and researchers; Rust is the deployment surface — embedded, server-side, or (inherited from sigil-lang's proven dual build) compiled to WASM for edge and browser. One engine, two idioms, identical semantics.

4 · What goes in

Two input paths, and the difference between them is the whole architecture:

  • Natural language — agent.run("58M, crushing chest pain…"). The perception step extracts typed instances, validated against the schema before they enter the world.
  • Structured facts — world.assert_(Patient(heart_rate=128, symptoms=[ChestPain])) or a FHIR/JSON payload mapped through the ontology. No LLM in the path at all. Monitors, EHR feeds, and sensors write directly; reasoning and workflow behave identically.

5 · Where the LLM is allowed to exist

BoundaryDirectionContract
Perception (sigil:PerceptionStep)NL → ontology instances Extraction constrained by a JSON schema derived from the ontology classes; confidence threshold; mandatory fallback step. Output is validated before it touches the world.
Narration (sigil:NarrationStep, optional)Proof tree → NL Renders the deterministic proof for humans ("Immediate because HR 128 exceeds 120 with chest pain"). Generates prose, never conclusions.
Everything else— No LLM. State, reasoning, workflow transitions, tool gating, verification: deterministic, traced, reproducible.

That's the entire neural surface: two declared transducer boundaries, both with typed contracts, both recorded in the trace with model, confidence, and fallback status. The LLM proposes; it never decides.

6 · One run, dissected

What actually happens inside agent.run("58M, crushing chest pain 20 min, HR 128, BP 92/60, diaphoretic") — the string is the only unstructured thing in the entire run:

agent.run("58M, crushing chest pain 20 min, HR 128, BP 92/60, diaphoretic")
│
│   runtime looks up triage:Triage → startsAt :Intake        [symbolic: graph lookup]
│
├── STEP 1  :Intake — PerceptionStep      ★ THE ONLY LLM MOMENT ★
│     a. JSON schema derived FROM ontology classes            [symbolic]
│     b. NL string + schema → claude-fable-5                  [NEURAL]
│          returns { heartRate: 128, systolic: 92, diastolic: 60,
│                    symptoms: [CrushingChestPain, Diaphoresis], onset: 20min }
│          confidence: 0.94
│     c. 0.94 ≥ 0.85 threshold → accept                       [symbolic]
│          (below → :EscalateToNurse; the LLM never guesses)
│     d. validation gate: 128 ∈ [0,300] ✓ classes exist ✓     [symbolic]
│          only NOW asserted into the World graph
│     └─ the LLM's job is over — it never sees the rules
│
├── STEP 2  :Assess — ReasoningStep                           [symbolic]
│     forward chaining:  r1: 128 exceeds 120 ✓
│                        hasSymptom :ChestPain? → CrushingChestPain ⊑ ChestPain
│                                                 (SNOMED subsumption) ✓
│     r1 FIRES → asserts :acuity :Immediate  (proof tree recorded)
│
├── STEP 3  :Route — ActionStep                               [symbolic]
│     precondition acuity isAssigned ✓ → ehr.assign_queue(patient, :Immediate)
│     (ordinary Python/Rust code — no LLM here either)
│
└── result:  .decision = triage:Immediate
             .proof    = r1: 128 > 120 ∧ CrushingChestPain ⊑ ChestPain
             .trace    = every step above, typed and replayable

Notice the two facts that made the decision come from different symbolic sources: 128 > 120 from the rule condition, CrushingChestPain ⊑ ChestPain from the imported SNOMED hierarchy. Nobody wrote a rule about crushing chest pain — subsumption inferred it. And if the vitals arrive as structured JSON from an EHR monitor, step 1 is skipped entirely; steps 2–3 behave identically.

7 · The symbolic core — why this isn't an LLM wrapper

The world-state is a typed graph, and the graph does real inferential work:

  • Subsumption. :CrushingChestPain ⊑ :ChestPain ⊑ :Symptom — rule r1 fires on the subclass without anyone writing that case, because the hierarchy (including imported SNOMED axioms) is part of inference.
  • Forward chaining. New facts propagate to a fixed point through ontology rules — assert HR 128 and acuity follows, with the derivation recorded.
  • Backward chaining. world.explain(":acuity :Immediate") returns the proof tree; world.prove(goal) drives goal-directed evaluation — the "why" is a query, not a log grep.
  • Constraints as physics. sigil:min/max, cardinalities, SHACL-style shapes — a heart rate of 1280 (unit typo) is rejected at the boundary, not discovered in an incident review.
  • Verification before execution. The BDD layer (ported from sigil-lang) proves completeness, conflict-freedom, dead-rule absence, and termination of the rule set at load time — with counterexample witnesses in domain terms the SME can read.
  • Traces as first-class output. Every run is a typed trajectory: perception steps (model, confidence), fired rules, proof trees, tool calls with satisfied preconditions. Audit log and training corpus are the same object.
The falsifiable claim: delete the LLM and the framework still runs — structured facts in, verified reasoning and workflows out. A wrapper dies without its model; here the model is a replaceable transducer at two declared boundaries of a symbolic machine. That's what "neuro-symbolic framework from day one" means, and it's testable: the entire test suite of the symbolic core runs with no model configured.

8 · Tools and the Bridge: who calls what

In every conventional agent stack, the LLM decides which tool to call and with what arguments — tool selection is a neural act. Sigil inverts it: tools are declared in the ontology with typed contracts, and the runtime invokes them when an ActionStep's preconditions hold in the graph. Arguments are read from the graph, not parsed out of model text.

tool declaration — part of the same ontology 
:ehr.assign_queue a sigil:Tool ;
    sigil:takes   [ :patient a :Patient ; :queue a :AcuityLevel ] ;  # args come from the graph
    sigil:effect  [ :patient :queuedAt sigil:now ] ;                 # declared effect on the world
    sigil:binding "mcp://ehr-server/assign_queue" .                  # or python fn, rust fn, http
  • No neural tool choice. There is no "model hallucinated a tool call with wrong args" failure class — no model sits in that path.
  • Tool outputs are untrusted, like LLM outputs. Return values pass the declared-effect validation gate before becoming facts — an EHR API returning garbage is rejected at the boundary.
  • Bindings are pluggable: Python callables, Rust fns, HTTP, and MCP servers — domain tools that already speak MCP are consumed, not rebuilt.
  • Escape hatch for open choices: a sigil:ProposalStep lets the LLM rank candidates — but only candidates whose preconditions already hold. Neural proposes among the legal; symbolic defines legal and executes.

Underneath sits the Bridge — a thin trait/protocol over provider SDKs directly (Anthropic, OpenAI, local ONNX/HF, deterministic mock for CI), inherited from sigil-lang's proven ModelBackend + ModelRegistry design: prefix routing, per-call timeouts, mandatory fallbacks. No LangChain, no delegated agent loop — Sigil's runtime is the loop; it needs a model client, not another orchestrator. And one ironic implementation detail: a PerceptionStep uses the provider's tool-use API backwards — one Messages call, a single tool named assert_facts whose schema is derived from the ontology, tool_choice forced. Machinery built to let models choose actions is used purely as a typed output channel. Tool choice stays symbolic; tool-use plumbing becomes typed I/O.

9 · How the Turtle gets written: agents author, the verifier gatekeeps

Raw Turtle is the storage format, not the SME experience — no clinician hand-writes triples, the same way no accountant hand-writes CSV. The authoring flow is a conversation with an agent (Claude), and it is itself neuro-symbolic, applying the runtime's own principle at design time: neural proposes, symbolic decides. 

SME describes protocol in plain language
   → agent generates Turtle draft
   → parse → shape validation (SHACL-style) → BDD verification
        # completeness gaps, conflicts, dead rules — found before the SME ever sees a triple
   → counterexamples, in domain terms, fed back to the agent
   → agent refines; loop until the ontology verifies
   → SME reviews a rendered summary of rules & workflows — never syntax
   → versioned, signed-off triage.ttl

Generated Turtle is never trusted, because it never needs to be — every draft passes the same symbolic gate the runtime enforces. This makes the authoring agent the framework's first consumer of its own verification API, and it's proven ground: sigil-lang built exactly this loop twice (the NL-to-Sigil generator with parse → check → auto-retry refinement, and the sigil code ReACT agent). Retargeting the output from .sigil to .ttl is the delta. Bonus, per the Vision tab: every authoring session yields NL→Turtle pairs — a second training corpus, for the authoring model rather than the runtime one. Owns its own phase: PRP-007.

The long betFrom Type 2/3 to a differentiable future

Everything in the Plan tab is, honestly placed, Kautz Type 2–3: a deterministic symbolic orchestrator with neural components for perception. The runtime itself has no weights — the only weights in the system are the LLM's. That constraint is not a dead end; it points at exactly one place where gradients can live, and it turns out to be the place we control the best data for.

The observation: our traces are better training data

A conventional agent framework produces trajectories of free-form text and ad-hoc tool calls — long, noisy, unverifiable. An ontology-grounded run produces something categorically better: a methodical trajectory of typed steps — perceive → ground into ontology terms → reason (with a proof tree) → act — where every symbolic step is deterministic and every outcome is checkable against the ontology. In training terms: clean loss-masking boundaries (the runtime's outputs are observations, never targets), and deterministic reward signals for free — did the extraction validate, did the proof hold, did the workflow reach its goal state.

This is precisely the TIR/CIR recipe from our research corpus (ToRA → DeepSeekMath → ReTool → NuminaMath), with one substitution: the executor is not a Python sandbox — it's the ontology runtime. The literature's convergent recipe applies almost verbatim: cold-start SFT on ~10–80k trajectories, then outcome-rewarded RL (GRPO), loss-mask executor output, mix non-domain data to avoid catastrophic forgetting.

1 · Run — agents execute domain workflows in production; every run emits a typed trajectory with proof trees.
2 · Filter — the runtime scores each trajectory deterministically: validated groundings, held proofs, reached goals. No human labeling, no LLM judge.
3 · Train — SFT + agentic RL on the filtered trajectories. The LLM is the differentiable layer; the harness gets compressed into its weights.
4 · Redeploy — the tuned model natively speaks ontology terms — fewer grounding failures, fewer retries, richer trajectories. The flywheel turns.

The honest taxonomy check

Fine-tuning on these traces is — by our own research doc's framing — behavioural cloning of a Type 2 harness into Type 3 weights. It makes the model natively fluent in the ontology; it does not make the symbolic step differentiable. The runtime still decides, deterministically, which is the product's guarantee and must never be traded away. Two paths lead beyond that ceiling:

  • Path A — differentiable rule subset (Scallop precedent). Because we chose RDFS-plus with Datalog-shaped rules, a provenance semiring can in principle be defined over a tractable subset, letting gradients flow through symbolic inference itself. Genuine Type 5; unproven at LLM scale; the strongest published template exists (Scallop, 45k lines of Rust).
  • Path B — a graph neural network over the ontology instance graph. Explicitly a thinking-out-loud item, not a commitment. The world-state is already a typed graph; a GNN (R-GCN-style) could learn soft inference or ranking over it — e.g., proposing which rules or groundings to try first, with gradients flowing through graph reasoning. Where it sits between Type 3 and Type 5 depends on whether it augments the reasoner (heuristic guidance — safe, keeps determinism) or replaces parts of it (soft inference — trades away the guarantee). Scoping this is an open research question, parked until the flywheel produces data.
What this asks of v1 — and it's cheap: design the trace schema as a training corpus from day one. Every trajectory serialized in a stable tagged format (the research doc's format survey applies: <llm-code>-family tags or special tokens), with explicit loss-mask boundaries and machine-readable outcome labels. That lands in PRP-002 (traces) and PRP-004 (agent loop) as requirements now, so the option stays open later at zero retrofit cost. Everything else in this tab spends nothing until the flywheel has data.

Checkpoint 10thesis sharpened

The loop, the workflow, and the ontology are one

"The agent loop in the ontology and the workflows are not different — they are all one… Claude Code is just a loop with tool uses. What we're building is an ontology-first approach: ontologies built for different domains, by us as subject-matter experts. That's what this framework is all about."

Shaped the plan → Three consequences locked in: (1) the ontology's roles grew from two to three — it now declares the agent loop and workflows themselves, so there is no per-domain orchestration code; (2) the formalism question resolved its direction: RDFS-plus, opening interop with existing domain ontologies like SNOMED and FIBO; (3) a Use Cases tab was added — the framework is proven domain-by-domain, and the next decision is which domain goes first.

Checkpoint 11vision

The differentiable extension: the LLM is the trainable layer

"There are no weights here — the only weights are the LLM. The ontology-based output is methodical, where a normal agent loop would produce a long output… agentic RL fine-tuning would take that and learn from it. Probably we can think of a scope to bring in a graph neural network — I'm just thinking out loud."

Shaped the plan → A Vision tab was added: the data-flywheel thesis (run → filter deterministically → SFT+RL → redeploy), grounded in the TIR/CIR research corpus already in sigil-lang; the honest taxonomy (trace fine-tuning is Type-2-cloned-into-Type-3, with Scallop-style semirings and GNN guidance as the two paths beyond); and one cheap v1 obligation — design the trace schema as a training corpus from day one, now a requirement in PRP-002 and PRP-004. The GNN angle is parked as an explicit open question, per your framing.

Checkpoint 12as-if-shipped

The framework outlined as if it already exists

"Imagine this framework is already built and you are writing a doc for it. Take the clinical triage use case… so that it evolves as a neuro-symbolic framework from day one rather than just another LLM wrapper."

Shaped the plan → A Technical Outline tab was added, using clinical triage end-to-end: the SME's single-artifact triage.ttl (domain + rules + workflow in one ontology), Python and Rust quickstarts against the same engine, the two input paths (NL via perception, structured facts with no LLM at all), the LLM confined to two declared transducer boundaries, and the symbolic graph core — subsumption, chaining, constraints, load-time BDD verification. These API shapes become the arguable starting point for PRP-001 through PRP-004.

Checkpoint 13authoring

Agents write the Turtle

"We want to address this by eventually having agents like Claude generate Turtle."

Shaped the plan → The SME-experience caveat became a feature with its own phase: PRP-007, the ontology authoring agent. The flow applies the framework's own principle at design time — Claude drafts Turtle, the verifier gatekeeps (parse → shape validation → BDD verification → domain-term counterexamples → refine), and the SME reviews rendered rules, never syntax. Proven ground: sigil-lang built this loop twice (NL-to-Sigil generator, sigil code agent); the delta is retargeting output to .ttl. Side effect: authoring sessions produce NL→Turtle training pairs, a second corpus for the Vision flywheel.
